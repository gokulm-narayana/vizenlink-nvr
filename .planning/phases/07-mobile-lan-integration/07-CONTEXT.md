# Phase 07: Mobile LAN Integration - Context & Architectural Boundaries

## Purpose
Phase 07 connects the VizenLink mobile application (Flutter) to the NVR over the Local Area Network (LAN). It provides zero-configuration discovery via mDNS, secure device pairing with revocable per-device tokens, live video streaming defaulted to low-bandwidth sub-streams, recorded history browsing with calendar dates and playback spans, unified NVR health/storage telemetry, and permission-gated camera and recording management (requirements `MOB-02` through `MOB-07`).

## In Scope Requirements
- **MOB-02**: LAN Discovery via mDNS / Zeroconf (`_vizenlink-nvr._tcp.local.`) with advertised API version and NVR metadata, plus manual direct IP fallback.
- **MOB-03**: Secure Device Pairing via direct credentials or QR-code scan, issuing per-device access and refresh tokens with administrative revocation (`AUTH-04`).
- **MOB-04**: Mobile Live Stream Relay through NVR with signed media tokens, defaulting to the camera's sub stream on mobile networks/screens.
- **MOB-05**: Mobile Recorded History Browsing and Playback: calendar days with footage, clip list with trigger annotations, and Range-capable video streaming.
- **MOB-06**: Mobile Health and Storage Telemetry: overall recorder state, disk utilization and retention estimation, and per-camera recording and connectivity status.
- **MOB-07**: Mobile Camera and Recording Management: adding and removing cameras, and updating recording modes, enforced with server-side RBAC (Owner/Admin required for add/remove, Viewers blocked).

## Architectural Boundaries & Principles
1. **mDNS Service Advertising (`MOB-02`):**
   - Uses `python-zeroconf` (`zeroconf`) to broadcast the NVR service on the local subnet.
   - Service type: `_vizenlink-nvr._tcp.local.`.
   - TXT record properties include `api_version="v1"`, `nvr_id`, `name`, `model`, `port`, and `tls="false"`.
   - Binds to network interfaces and deregisters gracefully on application shutdown.
2. **Device Identity & Token Lifecycle (`MOB-03`):**
   - Mobile devices receive distinct per-device tokens: a short-lived access token (15-60 min) and a long-lived refresh token.
   - Devices are registered in `paired_devices` with device name, platform (iOS/Android), paired timestamp, and `is_revoked` status.
   - When an administrator revokes a paired device, all active sessions and refresh requests for that device are immediately rejected (HTTP 401).
   - QR code pairing uses short-lived single-use pairing nonces (`qr_pairing_sessions`) generated by authenticated web sessions.
3. **Bandwidth-Aware Live Streaming (`MOB-04`):**
   - Mobile clients stream through NVR's MediaMTX proxy with signed media auth tokens (`action="read"`).
   - Defaults to the camera's `sub` stream profile to conserve mobile network and rendering bandwidth, while permitting explicit `main` stream switching.
4. **Mobile Recordings Format Compatibility (`MOB-05`):**
   - Endpoint `/api/v1/mobile/cameras/{camera_id}/recording-dates` returns available dates.
   - Endpoint `/api/v1/mobile/cameras/{camera_id}/recordings` returns structured spans including start, end, duration, size, and trigger classification (`continuous`, `motion`, `line_cross`, `tamper`).
   - Video playback URLs support HTTP 206 Partial Content byte ranges.
5. **Server-Side RBAC Invariant (`MOB-07`):**
   - Mobile authentication inherits user roles (`owner`, `operator`, `viewer`).
   - Administrative camera operations (add/remove) and recording mode changes strictly enforce RBAC server-side; viewers attempting modifications receive HTTP 403 Forbidden.
