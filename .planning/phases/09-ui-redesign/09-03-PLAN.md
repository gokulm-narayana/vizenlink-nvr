<objective>
Make camera onboarding through the API fail closed when the server has no runtime vault, instead of sealing credentials with the all-zero in-memory test key (D-18, owner-approved backend addition). Give the real `Runtime` the opened vault so an app built the production way seals with it, and prove that end to end with a pytest through the production app factory.

Purpose: Core value is "never miss footage". Today `_resolve_vault` silently seals web-added credentials with a key the recorder can never read, so a camera added from the web would never record and nobody would know why. Failing closed turns that into a clear, visible error. Backend scope for Phase 9 is the `/cam` proxy (09-02), the site time zone (09-02) and this change only.
Output: `Runtime.vault`, a fail-closed `_resolve_vault`, a new pytest file, and the two existing camera API tests updated to inject an explicit test vault.
</objective>

Facts verified while planning:
- `_resolve_vault` (cameras.py) returns `runtime.vault` when present, otherwise creates `app.state.vault = Vault(b"0" * 32, "test-vault-key", "memory")`. The `Runtime` dataclass (`services/runtime.py`) has no `vault` field, only `vault_status`, so even an app built with a real runtime seals with the all-zero key today.
- `open_runtime` already runs `initialise_vault(rt)` (creates the key and canary on a fresh data dir). `open_vault(rt)` (`secrets/vault.py`) returns the operational `Vault` after a passing canary check and raises `CredentialsUnreadable` otherwise.
- `camera_settings.get_vault` lazily creates the same all-zero vault on `app.state.vault`. It is out of D-18 scope and stays unchanged, but `_resolve_vault` must not read `app.state.vault`, or that lazy object would reintroduce the fallback.
- `tests/conftest.py` sets `NVR_SECRETS_BACKEND=file`, so `open_runtime` on a tmp data dir creates a file key.
- Only `tests/integration/test_api_cameras.py` and `tests/integration/test_phase3_tracer.py` POST `/api/v1/cameras`; both build the app with a session factory only and rely on the fallback today.
- `services.*` is under mypy strict.
- No production entry point passes `runtime=` to `create_app` today (the committed module-level `app` and the owner's uncommitted `nvr run` build it without one). After this plan those servers answer POST /cameras with 503 by design. Wiring `open_runtime` into the owner's `nvr run` is owner work in an uncommitted file this plan must not touch; record it in the SUMMARY as an owner follow-up. 09-10's e2e launcher builds the app from `open_runtime`, so e2e camera creation works.
