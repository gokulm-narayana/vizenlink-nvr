API facts (`cameras.py`): `POST /api/v1/cameras` requires Operator. `CameraCreateRequest` has `serial` and `host` required (min 1), and defaults `https_port 443`, `name "Camera"`, `location "Default"`, `group_tag "default"`, `username "admin"`, `password "admin123"`, `streams []`. `StreamInput` defaults are `role main, profile_token Profile_1, profile_name MainStream, venc_token VideoEncoder_1, codec H264, 1920x1080, transport tcp, scheme rtsp, port 554, path /stream1`. A duplicate serial returns 409. The endpoint inserts a registry record only; it does not probe the camera (the CLI does).

Planner decisions (record in the SUMMARY):
- The sub stream defaults to `role "sub"`, `profile_token "Profile_2"`, `profile_name "SubStream"`, `venc_token "VideoEncoder_2"`, with the other values from the API defaults, so it never reuses the main stream's tokens (Pitfall 10).
- The UI always sends `name` (the serial when blank), `location` and `group_tag` explicitly ("Default" and "default" when blank, matching the API).

Owner-visible risk, recorded as a SUMMARY note and not changed here: `_resolve_vault` falls back to an in-memory test vault when the API app has no Runtime. The owner's uncommitted `nvr run` builds the app with only a session factory, so a camera added through this wizard on such a server may store credentials the recorder cannot read. Verify with a real recorder before relying on web-added cameras (see human-check).

Only this plan edits `features/cameras/add/` and the new pytest. `features/cameras/` outside `add/` belongs to 09-15.
</context>
